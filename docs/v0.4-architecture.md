# RetroPad v0.4 architecture

## Product definition

RetroPad v0.4 treats the Android phone as the console and the external device as a display.

The phone continues to run FullRoid and owns the ROM, emulator, save state, controller state, and game audio/video source. RetroPad captures that output and streams it over the local network.

## Primary flow

1. User opens `display.html` on a Mac, Windows PC, or compatible TV browser.
2. Display creates a six-character room and QR code.
3. RetroPad Android scans the QR and joins the room as role `android`.
4. Android starts MediaProjection capture.
5. Android creates a WebRTC offer and sends SDP/ICE through the RetroPad signaling server.
6. Browser display answers and renders the incoming media stream fullscreen.
7. RetroPad controller overlay remains on the phone while FullRoid runs.

## Signaling

The Node WebSocket server is signaling only. It relays:

- `offer`
- `answer`
- `ice`
- `stream-meta`

between `android` and `display` peers in the same room.

Game media does not pass through Node. WebRTC should establish a direct local-network media path whenever possible.

## QR payload

Current development URI:

```text
retropad://pair?host=192.168.1.8&port=8080&room=ABC123
```

The native Android app will register the `retropad://` scheme and use the host/port/room values to connect to signaling.

For early development before app-link registration is complete, the same fields can be entered manually.

## Android components

Planned native components:

- QR scanner / deep-link handler
- foreground capture service
- Android MediaProjection capture
- WebRTC peer connection
- hardware H.264 encoding where available
- audio capture where Android/FullRoid permits it
- console-profile controller overlay
- FullRoid input integration adapter

## FullRoid input integration

This is the major unknown in v0.4.

A normal Android overlay cannot automatically control another app. RetroPad must determine which permitted Android input route FullRoid accepts. Candidate approaches should be tested in this order:

1. FullRoid-supported external controller/input API, if available.
2. Android accessibility-based action/input bridge, if it can provide the required game-control fidelity.
3. Virtual/input-device route available on the target Android device without requiring unsafe system modifications.
4. If FullRoid exposes no workable input path, keep FullRoid as the game source but require its own on-screen controls to remain accessible beneath/alongside the RetroPad overlay until a better integration is available.

Do not assume arbitrary input injection is possible from an ordinary Android app.

## Latency goals

The display path is designed for local Wi-Fi and should prioritize latency over image quality.

Initial targets:

- 720p60 or 1080p60 depending on encoder capability
- hardware H.264
- no cloud relay in normal LAN use
- minimal jitter buffer
- controller UI processed locally on Android

## Legacy v0.3

The Python virtual-controller receivers and old phone PWA remain in the repository as reference. They are no longer required for the v0.4 Android-as-console architecture.
